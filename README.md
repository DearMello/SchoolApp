SchoolApp is a RESTful Web API built with ASP.NET Core 8 that implements a school management system covering students, teachers, courses, enrollments, and grades within a single cohesive solution. The project follows Clean Architecture principles, separating concerns across four independent layers: Domain, Application, Infrastructure, and API. The Domain layer is the innermost layer and carries no external dependencies, defining only the core entities, enums, and repository interfaces that the rest of the system depends on. The Application layer sits above Domain and contains all business logic, organized into service interfaces, service implementations, and DTO classes for each feature area. The Infrastructure layer is responsible for all data access concerns, providing Entity Framework Core implementations of the repository interfaces and configuring the SQL Server database through a central DbContext. The API layer is the entry point of the application, exposing HTTP endpoints through ASP.NET Core controllers and wiring everything together through dependency injection configured in Program.cs.
The system manages five entities: Student, Teacher, Course, Enrollment, and Grade. A Student holds personal information such as first name, last name, email, phone, date of birth, and a unique student number, along with an IsActive flag for soft deactivation. A Teacher stores similar contact details plus a department field and an IsActive flag, and can be assigned to multiple courses. A Course belongs to exactly one Teacher and holds a unique course code, a name, a description, a credit count, and a capacity limit that controls how many students can enroll. An Enrollment represents the relationship between a Student and a Course, recording the enrollment date and a status that can be Active, Dropped, Completed, or Failed. A Grade is linked one-to-one with an Enrollment and stores a numeric score, a calculated letter grade, an optional remarks field, and the date the grade was assigned.
All five entities inherit from a shared BaseEntity class that provides Id, CreatedAt, and UpdatedAt fields, keeping timestamp management consistent across the entire domain. The EnrollmentStatus enum gives the enrollment lifecycle a type-safe representation, making status transitions explicit and readable throughout the codebase. The repository pattern is implemented generically through an IRepository interface that defines GetByIdAsync, GetAllAsync, AddAsync, Update, Delete, and SaveChangesAsync, reducing boilerplate across all five concrete repository classes. Each entity also has a dedicated extended repository interface — IStudentRepository, ITeacherRepository, ICourseRepository, IEnrollmentRepository, and IGradeRepository — that adds domain-specific query methods such as GetByStudentNumberAsync, GetByDepartmentAsync, GetByCodeAsync, IsAlreadyEnrolledAsync, GetEnrollmentCountByCourseAsync, and GetByEnrollmentIdAsync.
The EnrollmentService contains the most important business logic in the application, enforcing two rules before creating an enrollment: it checks whether the student is already enrolled in the requested course using IsAlreadyEnrolledAsync, and it verifies that the current enrollment count has not reached the course capacity, throwing an InvalidOperationException with a descriptive message if either condition fails. The grade assignment logic in EnrollmentService also handles both creation and update in a single AssignGradeAsync method — if a grade already exists for the given enrollment it updates it in place, and if not it creates a new one, keeping the API surface simple for callers. Letter grades are computed automatically from the numeric score using a switch expression that maps 90 and above to A, 80 to B, 70 to C, 60 to D, and anything below to F, so teachers only need to submit a score and the system handles the rest.
The SchoolDbContext configures all five entities using the fluent API inside OnModelCreating, applying column constraints, max lengths, and unique indexes at the database level. StudentNumber and Email on Student are each indexed as unique, preventing duplicate registrations at the persistence layer rather than relying only on application-level checks. The Course entity enforces a unique index on Code so no two courses can share the same identifier. The Enrollment entity has a composite unique index on the StudentId and CourseId pair, providing a database-level guarantee against duplicate enrollments even under concurrent requests. The Grade entity is mapped as a one-to-one relationship with Enrollment using a dedicated foreign key, and cascade delete is enabled so that removing an enrollment automatically cleans up its associated grade.
Each entity has three DTO classes — a read DTO, a create DTO, and an update DTO — keeping request and response shapes strictly separate from domain models. The CourseDto includes an EnrolledCount field that is populated at the service level by querying the enrollment repository, giving clients live capacity information without a separate API call. The EnrollmentDto flattens student and course details like full name, student number, course name, and course code directly into the response, and also embeds the associated GradeDto when one exists, so a single GET request returns a complete picture of the enrollment. The API exposes four controllers — StudentsController, TeachersController, CoursesController, and EnrollmentsController — each following the same consistent response conventions: 200 for reads, 201 with a location header for creates, 204 for deletes and drops, and 404 when a resource is not found. The EnrollmentsController adds a PATCH endpoint at /api/enrollments/{id}/drop to transition an enrollment to Dropped status, and a POST endpoint at /api/enrollments/grades to assign or update a grade, with business rule violations returned as 400 Bad Request responses containing a descriptive message field.
